# User Registration API

A user registration REST API built with Spring Boot 4 and Java 25. The service validates incoming registration requests, checks them against a configurable, database-driven set of eligibility rules, and exposes a filterable, paginated search endpoint over registered users.

## Features

- **User registration** (`POST /api/users`) with bean-validation on all fields (username, birthdate, country, phone number, gender)
- **Duplicate detection** on the composite key `(username, birthdate, countryOfResidence)`
- **Configurable eligibility rules** stored in the database, combining multiple criteria (country, age) via `AND`/`OR` logic with per-criterion operators (`EQ`, `NEQ`, `GT`, `GTE`, `LT`, `LTE`, `BETWEEN`, `IN`, `NOT_IN`)
- **Dynamic, paginated user search** (`GET /api/users`) using a generic JPA `Specification` that filters on any entity field via query parameters
- **Consistent error responses** with structured error codes via a global exception handler
- **Database migrations** managed with Liquibase, including seed data for a default eligibility rule and sample users

### Run the application

```bash
./mvnw spring-boot:run
```

The API starts on **`http://localhost:8080`**.

### Database

The app uses a **file-based H2 database** at `./data/usersdb` (kept between restarts, schema fully managed by Liquibase). On first run, Liquibase will:

1. Create the `users`, `eligibility_rules`, and `eligibility_criteria` tables
2. Add the foreign key from `eligibility_criteria` to `eligibility_rules`
3. Seed a default eligibility rule, **"French adults"** — `country = FR AND age >= 18`
4. Load a set of sample users from `users.csv`

The H2 web console is available at:

```
http://localhost:8080/h2-console
```

Connect using:
- **JDBC URL**: `jdbc:h2:file:./data/usersdb`
- **Username**: `sa`
- **Password**: *(empty)*

### Resetting the database

The H2 database files persist between restarts (`./data/usersdb.mv.db`, `./data/usersdb.trace.db`). To wipe them and start from a clean schema (re-applied by Liquibase on next launch, including seed data), use the `reset-db` Maven profile instead of deleting the files manually:

```bash
mvn initialize -P reset-db
```

Or combined with a normal run, to reset and start in one command:

```bash
mvn spring-boot:run -P reset-db
```

> If the app or your IDE's Java language server is still running, Windows may lock the database files and the reset will fail silently or error out — stop the running app first.

## API reference

All endpoints are under `/api/users`. Security currently permits all requests to `/api/**` (no authentication required yet).

### `POST /api/users` — Register a user

**Request body:**

```json
{
  "username": "isabelle.martin",
  "birthdate": "1995-06-15",
  "countryOfResidence": "FR",
  "phoneNumber": "+33612345678",
  "gender": "FEMALE"
}
```

| Field | Required | Constraints |
|---|---|---|
| `username` | yes | 3–50 characters, not blank |
| `birthdate` | yes | must be in the past |
| `countryOfResidence` | yes | valid `Country` enum value (ISO 3166-1 alpha-2) |
| `phoneNumber` | no | max 20 chars, digits with optional leading `+` |
| `gender` | no | valid `Gender` enum value |

**Responses:**

| Status | Condition |
|---|---|
| `201 Created` | User registered successfully — returns the created `UserResponse` |
| `400 Bad Request` | Validation failure (missing/invalid field) or malformed JSON |
| `409 Conflict` | A user with the same `username` + `birthdate` + `countryOfResidence` already exists |
| `422 Unprocessable Entity` | User does not satisfy the active eligibility rules |

### `GET /api/users` — Search users

Supports pagination, sorting, and dynamic filtering by any field on the `User` entity.

**Pagination & sorting parameters** (standard Spring Data):

| Param | Example | Default |
|---|---|---|
| `page` | `page=0` | `0` |
| `size` | `size=10` | `20` |
| `sort` | `sort=birthdate,desc` | `username` ascending |

**Filter parameters** — any other query parameter is matched against the corresponding `User` field:

| Field type | Matching strategy | Example |
|---|---|---|
| `String` (e.g. `username`) | case-insensitive **contains** | `?username=isa` matches `isabelle`, `Lisa` |
| `Enum` (e.g. `gender`, `countryOfResidence`) | case-insensitive **contains** on the enum name | `?gender=REF` matches `PREFER_NOT_TO_SAY` |
| `LocalDate` (e.g. `birthdate`) | **exact match**, format `yyyy-MM-dd` | `?birthdate=1993-06-30` |
| Numeric (e.g. `id`) | **exact match** | `?id=42` |

**Example requests:**

```
GET /api/users?page=0&size=10
GET /api/users?username=isa
GET /api/users?gender=FEMALE
GET /api/users?gender=ref          # partial enum match
GET /api/users?birthdate=1993-06-30
GET /api/users?username=be&gender=FEMALE   # combined filters (AND)
```

A malformed date filter (e.g. `?birthdate=not-a-date`) currently returns a `500` — see [Known limitations](#known-limitations--next-steps).

### `GET /api/users/id` — get user by id 

Fetch a single `User` entity by its numeric id.

**Path parameter** : `id` (numeric)

**Responses:**

| Status | Condition |
|---|---|
| `200 Ok` | User found successfully — returns the found `UserResponse` |
| `404 Not Found` | When no user exists with the given id |

**Example requests:**

```
GET /api/users/12
```

### Error response format

```json
{
  "code": "409",
  "message": "Object User with username, birthdate, country: 'isabelle.martin, 1995-06-15, France' already exists",
  "fieldErrors": null,
  "timestamp": "2026-06-19T09:36:33.017528300Z"
}
```

For validation errors (`400`), `fieldErrors` is populated per invalid field:

```json
{
  "code": "400",
  "message": "Validation failed",
  "fieldErrors": [
    { "field": "username", "message": "Username is required", "rejectedValue": null }
  ],
  "timestamp": "2026-06-19T09:36:33.017528300Z"
}
```

| Code | HTTP status |
|---|---|
| `400` | Bad Request |
| `409` | Conflict |
| `422` | Unprocessable Entity |
| `500` | Internal Server Error |

## Eligibility rules

Eligibility is **data-driven**, not hardcoded. Rules live in the `eligibility_rules` table, each with a set of `eligibility_criteria` rows combined by the rule's `operator` (`AND` / `OR`).

The seeded default rule, **"French adults"**, requires:
- `COUNTRY EQ FR`
- `AGE GTE 18`

combined with `AND` — meaning only French residents 18 or older can register out of the box. Add or modify rows in `eligibility_rules` / `eligibility_criteria` (or a new Liquibase changeset) to change this without touching application code.

Supported criterion types: `COUNTRY`, `AGE`, `CUSTOM` (extensible placeholder).
Supported operators: `EQ`, `NEQ`, `GT`, `GTE`, `LT`, `LTE`, `BETWEEN`, `IN`, `NOT_IN`.

## Testing strategy

- **Unit tests** (`@ExtendWith(MockitoExtension.class)`) for `UserService`, `EligibilityRuleService`, and `GenericSpecification`, using `@Mock` / `@InjectMocks`, AssertJ assertions, and EasyRandom for fixture generation
- **Controller tests** (`@WebMvcTest`) for `UserController`, covering every validation rule, both business exceptions, and pagination/filter delegation, using `@MockitoBean` for the service layer
- Run `./mvnw clean verify` to execute the full suite and generate the JaCoCo coverage report

## Known limitations / next steps

- No authentication/authorization is enforced yet — `/api/**` is fully public (remove exclude = UserDetailsServiceAutoConfiguration.class from main class)
- No audit fields are aconfigured 
- No role security is enforced
- Postman Collection would need to evolve to test login, feed token to request, test 403 errors 
- A malformed `LocalDate` filter value on `GET /api/users` (e.g. `birthdate=not-a-date`) currently surfaces as a `500 Internal Server Error` rather than a `400` — this is exercised by the Postman collection's "filter invalid date" request and is a known gap to close
- A malformed `id` value on `GET /api/users/id` (e.g. not a numeric id) currently surfaces as a `500 Internal Server Error` rather than a `400` — this is exercised by the Postman collection's "id not numeric" request and is a known gap to close
- `GET /api/users` filtering does not yet support range queries (e.g. age between two dates) — only exact/contains matching per field
- Property files of different environement not established yet
- For future database implementation, create schemas application and liquibase
- No implementation of a fixed and PageResponse for user retreival
